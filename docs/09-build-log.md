## 4. บั๊กที่พบและแก้ — คุ้มค่าที่สุดของการทดลองนี้

### บั๊ก 1 · mask จับได้แค่วงแหวน ทำให้ความกลมต่ำจนถูกตัดทิ้งหมด

**อาการ:** recall เป็น 0.000 บน icon ที่ไม่ทับกัน precision 0.134

**สาเหตุ:** team color mask จับสีได้เฉพาะ *วงแหวน* รอบนอกของ icon
เพราะเนื้อในคือ portrait ของฮีโร่ซึ่งเป็นสีอะไรก็ได้
blob จึงออกมาเป็นวงแหวนกลวง ที่มีความกลมราว **0.42**
แล้วถูกตัวกรอง `min_circularity = 0.60` ตัดทิ้งทั้งหมด

**แก้:** เติมรูใน blob ก่อนวิเคราะห์ (`fill_holes`)
วงแหวนกลายเป็นวงกลมตัน ความกลมขึ้นเป็นราว 0.95

| | ก่อน | หลัง |
|---|---|---|
| precision | 0.134 | 0.912 |
| recall (ไม่ทับ) | 0.000 | 0.884 |

**นี่คือบั๊กที่จะกินเวลาหลายวันถ้าไปเจอบนคลิปจริง** เพราะอาการคือ
"ตรวจไม่เจออะไรเลย" ซึ่งชวนให้ไปโทษ threshold สีหรือ background
ทั้งที่ต้นเหตุอยู่ที่รูปทรงของ blob

### บั๊ก 2 · เกณฑ์แยก blob กว้างเกินไป การแยกจึงไม่เคยทำงาน

**อาการ:** recall ของ icon ที่ทับกันได้ 0.18 ทั้งที่มีโค้ดแยก blob อยู่แล้ว

**สาเหตุ:** โค้ดเรียกการแยกเมื่อ `area > area_hi` โดย `area_hi` คือ
ขอบบนของขนาดที่ยอมรับสำหรับ icon **หนึ่งตัว** ซึ่งเผื่อไว้ถึง 1.45 เท่า
icon สองตัวที่ทับกันมีพื้นที่รวมราว 1.6 เท่าของตัวเดียว ซึ่งยังไม่ถึง `area_hi`
เงื่อนไขจึงไม่เคยเป็นจริง

**แก้:** เพิ่ม `IconSpec.nominal_area` (พื้นที่ของ icon เดี่ยวโดยประมาณ)
แล้วประเมินจำนวน icon จากสองสัญญาณ

```
k_area   = round(area / nominal_area)
k_peaks  = จำนวนยอดใน distance transform
k        = max(k_area, k_peaks)
```

recall ของ icon ที่ทับกัน 0.18 → 0.46

### บั๊ก 3 · ยอดปลอมใน distance transform ทำให้แยก blob เกินจริง

**อาการ:** icon สองตัวถูกแยกออกเป็นสามจุด

**สาเหตุ:** distance transform ของ blob เล็กมีที่ราบ (plateau)
ทำให้ local maxima ออกมาติดกันหลายยอด ซึ่งเป็น icon ตัวเดียวกัน

**แก้:** รวมยอดที่อยู่ใกล้กว่า 0.8 เท่าของรัศมี icon เข้าเป็นยอดเดียว

precision 0.954 → 0.968 และทำให้ผ่านเกณฑ์ precision ทุก seed

## 5. การค้นพบเชิงออกแบบ · หน้าต่าง background ยิ่งยาวยิ่งดี

เอกสาร [04-vision-pipeline.md](04-vision-pipeline.md) เดิมสรุปว่าต้องใช้
**rolling median หน้าต่างสั้น 60–90 วินาที** เพราะป้อมจางสีลงตลอดเกม

**วัดจริงแล้วตรงข้าม**

| หน้าต่าง | precision | recall (ไม่ทับ) |
|---------|-----------|-----------------|
| 75 วินาที | 0.919 | 0.926 |
| ทั้งคลิป | **0.972** | **0.969** |

**สาเหตุ:** ฮีโร่ที่อยู่นิ่งนาน เช่น ฟาร์มป่าหรือยืนเลนไม่ขยับ
จะครองเวลาเกินครึ่งของหน้าต่างสั้น แล้วถูกนับเป็นพื้นหลังไปเลย
detector จึงมองไม่เห็นตัวเอง

พบหลักฐานชัดจากการที่ icon ทีมน้ำเงินหายมากกว่าทีมแดง 3.5 เท่า
และ 158 จาก 512 ครั้งที่พลาดเกิดบนแม่น้ำ ซึ่งเป็นบริเวณที่ฮีโร่เดินช้า

ส่วนความกังวลเรื่องป้อม: ป้อมเป็นสี่เหลี่ยมเล็กที่พื้นที่ต่ำกว่าเกณฑ์ขนาด icon
ตัวกรองขนาดจึงจัดการได้อยู่แล้ว และถ้ายังหลุด ให้ใส่ `tower_positions`
ใน layout config เพื่อ mask ทิ้งตรง ๆ เพราะป้อมอยู่ตำแหน่งคงที่ที่รู้อยู่แล้ว

**ค่าเริ่มต้นใหม่:** `bg_window_sec = 600.0`

## 6. สมมติฐานที่ทดสอบแล้วผิด · background จาก percentile ของความอิ่มสี

**แนวคิด:** hero icon เป็นสีทีมที่อิ่มสีสูง ส่วนภูมิประเทศอิ่มสีต่ำกว่า
ถ้าเลือกค่าที่ percentile ต่ำของความอิ่มสีต่อ pixel แทน median
น่าจะทนต่อฮีโร่ที่อยู่นิ่งได้

**ผล: แย่กว่าทุก seed**

| seed | median | low saturation |
|------|--------|----------------|
| 0 | 0.956 | 0.888 |
| 1 | 0.915 | 0.878 |
| 2 | 0.947 | 0.885 |
| 3 | 0.964 | 0.942 |

**สาเหตุ:** การเลือกทีละ pixel จากคนละเฟรมทำให้ภาพพื้นหลังไม่กลมกลืน
เกิด noise ระดับ pixel แล้ว residual สูงขึ้นทั้งภาพ

**ถอดออกแล้ว อย่ากลับไปลองอีก** บันทึกไว้ในหัวไฟล์ `rov/minimap/background.py`

## 7. ผลปัจจุบันบนชุดสังเคราะห์

`rov eval-synthetic --duration 240 --seeds 4`

| seed | precision | recall (ไม่ทับ) | recall (ทับกัน) | error | ผล |
|------|-----------|-----------------|-----------------|-------|-----|
| 0 | 0.9685 | 0.9732 | 0.7434 | 0.00387 | ผ่าน |
| 1 | 0.9569 | 0.9322 | 0.7328 | 0.00410 | ไม่ผ่าน |
| 2 | 0.9700 | 0.9515 | 0.7694 | 0.00411 | ผ่าน |
| 3 | 0.9681 | 0.9652 | 0.7394 | 0.00363 | ผ่าน |

**ผ่าน 3 จาก 4 seed** · seed 1 พลาดเกณฑ์ `recall_clear` ที่ 0.932 เทียบเกณฑ์ 0.95

**สาเหตุของ seed 1:** ตัวกำเนิดสุ่มความเร็ววงโคจรของฮีโร่ seed นี้ได้ฮีโร่ที่
เดินช้ามากจนเกือบนิ่ง ซึ่งยังถูกกลืนเข้าพื้นหลังแม้หน้าต่างจะยาว

ในเกมจริงฮีโร่ข้ามแมพในราว 15–20 วินาที และมีการกลับฐาน จึงไม่มีใครนิ่ง
อยู่จุดเดียวนานขนาดนั้น กรณีนี้จึงโหดกว่าความจริง

**แต่ต้องตรวจซ้ำกับคลิปจริง** และนี่คือรายการอันดับหนึ่งที่ต้องดูตอนได้คลิปมา

## 12 — รอบที่สาม: ปลดล็อก Composition, Scouting และซ่อมข้อมูลที่เพี้ยนเงียบ ๆ

รอบนี้ตั้งต้นจากการตรวจว่าอะไรในโครงการ "เขียนเสร็จแล้วแต่ใช้งานไม่ได้จริง"
คำตอบคือ Composition Engine 282 บรรทัด ที่ไม่เคยรันสำเร็จสักครั้ง

### 12.1 บั๊กข้อมูลสี่ตัวที่ไม่มีใครเห็น

ทั้งสี่ตัวทำให้สถิติเพี้ยนโดยไม่มี error โผล่มาเลย ซึ่งเป็นชนิดที่อันตรายที่สุด

**ก) heroes.yaml ขาดฮีโร่ไป 26 ตัว**

`rov draft heroes-init` รับ tournament เดียวเป็น argument และค่าเริ่มต้นคือ
RPL 2026 Summer เท่านั้น ฮีโร่ที่เล่นเฉพาะในลีกอื่นจึงไม่เคยเข้าไฟล์

    tamyn    presence 15%  ถูกแบน 110 ครั้ง   ไม่มีในไฟล์
    astrid   presence 13%  ถูกแบน  63 ครั้ง   ไม่มีในไฟล์

`tamyn` คือตัวที่ถูกแบนบ่อยเป็นอันดับต้น ๆ ของเมตา แต่บนกระดานเว็บมันไม่มี
class ไม่มีรูป และไม่มีวันถูกกรอก attribute ได้เลย

แก้: `heroes-init` ใช้ทุกรายการใน cache เป็นค่าเริ่มต้น (`--one` ถ้าอยากได้รายการเดียว)

**ข) ชื่อฮีโร่ถูกนับแยกเป็นสองก้อน**

`normalize_hero_id()` เดิมจัดการ apostrophe กับช่องว่างได้ แต่จับชื่อย่อไม่ได้

    flw_mm      37 pick   Portal เขียน "Flowborn/Marksman" หน้าแมตช์ย่อเหลือ MM
    bolt_baron  44 pick   คือตัวเดียวกับ sikong (1 pick) — Sikong Zhen = Bolt Baron
    diaochan     1 pick   คู่กับ diao_chan
    lubu         2 pick   คู่กับ lu_bu

`flw_mm` หนักที่สุด — 37 pick ลอยอยู่ในรูปของ id ที่ไม่มีฮีโร่รองรับ
แก้ด้วยตาราง `HERO_ALIASES` ที่ทุกบรรทัดมีหลักฐานกำกับ · ฮีโร่ 122 → 119 ตัว

**ค) `rov draft sim` ไม่ส่ง lane_usage**

กระดานเว็บกับ CLI ใช้ `recommend()` ตัวเดียวกัน แต่ CLI ไม่ส่ง `lane_usage` เข้าไป
ฟีเจอร์ "แบนตามตำแหน่งที่อีกฝั่งยังไม่เปิด" จึงมีแค่บนเว็บ
สองหน้าจอให้คำตอบต่างกันโดยที่ผู้ใช้ไม่มีทางรู้ว่าอันไหนถูก

**ง) หน้าต่าง "N วันล่าสุด" เลื่อนตามอนาคต**

Liquipedia ลงตารางแมตช์ล่วงหน้า ชุดข้อมูลจึงมีวันที่ลากไปถึง 2026-10-31
ทั้งที่แมตช์ล่าสุดที่แข่งจริงคือ 2026-09-06 ถ้านับรวม หน้าต่าง 120 วัน
จะกินแมตช์จริงน้อยกว่าที่ควร — `date_range()` จึงนับเฉพาะซีรีส์ที่แข่งไปแล้ว

### 12.2 ปลดล็อก Composition Engine

ปัญหาไม่ใช่โค้ด แต่คือ heroes.yaml ว่าง 0/119 มาตลอด

หลักเดิมของโครงการคือ "ระบบห้ามเดาค่าเชิงคุณภาพ" ซึ่งถูก แต่ผลข้างเคียงคือ
เครื่องมือที่เขียนเสร็จแล้วไม่เคยถูกใช้เลยสักครั้ง ทางออกที่เลือกคือ
**แยกที่มาให้อ่านด้วยเครื่องได้ แทนการห้ามหรือปล่อยผ่าน**

เพิ่มช่อง `Hero.filled_kind` สามค่า

    derived    คำนวณจากแมตช์จริง หรือยกมาจาก Liquipedia ตรง ๆ
    assistant  ผู้ช่วย AI ประเมินจากหลักฐานที่อ้างอิงได้
    human      คนที่รู้เกมประเมินเอง — น่าเชื่อที่สุด

`composition.analyze()` ขึ้นคำเตือนทุกครั้งที่คอมพ์มีตัวที่ `assistant` กรอก
และกระดานเว็บก็ขึ้นเหมือนกัน · `apply_hero_assessment.py` ไม่ทับตัวที่เป็น `human`

**หลักฐานที่ใช้ประเมิน** — `rov/draft/importer/herotraits.py` ดึงข้อเท็จจริง
จากหน้าฮีโร่ของ Liquipedia แล้วหยุดที่ข้อเท็จจริง ไม่แปลงเป็นคะแนนให้

    |dmg = mgc                          ชนิดดาเมจ
    |type = {{SkillTextID|red|Stun}}    ผลของสกิล -> แยก hard/soft CC, heal, dash
    |lane1 = darkslayer                 ตำแหน่งที่เกมกำหนด

สองบั๊กที่เทสต์จับได้ตอนเขียน

- regex `\{\{SkillCard(.*?)\n\}\}` พลาดการ์ดที่เขียนรวบบรรทัดเดียว และถ้าใช้
  non-greedy หา `}}` ตัวแรกจะไปจบที่วงเล็บของ `{{SkillTextID}}` ข้างใน
  แก้เป็นการนับวงเล็บให้สมดุลแทน
- เทียบป้ายสกิลแบบเท่ากันเป๊ะทำให้ `Self Damage Reduction` หลุด
  เปลี่ยนเป็นเทียบขอบคำ ซึ่งยังกัน `Discharge` ไม่ให้เข้าเงื่อนไข `charge`

ผลลัพธ์: กรอกครบ 30 ตัว = **72% ของ pick+ban ที่เกิดขึ้นจริง** ในชุดข้อมูล
เลนของแต่ละตัวมาจาก `lane_usage` ของเราเอง ไม่ได้เอาจากวิกิ
เพราะวิกิบอกตำแหน่งตามที่เกมออกแบบ ส่วนข้อมูลเราบอกว่ามืออาชีพเล่นจริงตรงไหน
(เช่น Rouie — วิกิว่า roam แต่ในข้อมูลลงช่องมิด 91% จาก 195 เกม)

### 12.3 Scouting ต่อทีม — ข้อมูลที่มีอยู่แล้วแต่ถูกทิ้ง

`parser.py` เก็บ `team1` `team2` `date` มาตั้งแต่ต้น แต่ไม่มีโมดูลไหนใช้เลย
ใน cache มี **305 ซีรีส์ · 20 ทีม · ข้อมูลข้ามหนึ่งปีเต็ม** ที่ไม่เคยถูกแตะ

`rov/draft/scouting.py` ตอบคำถามที่ `stats.py` ตอบไม่ได้

    stats.py    ลีกนี้ให้ค่าฮีโร่ตัวไหน   — ค่าเฉลี่ยข้ามทุกทีม
    scouting.py ทีมนี้เล่นอะไร           — ซึ่งเป็นสิ่งที่โค้ชใช้จริงตอนแบน

`target_bans()` รวมสามอย่าง: เขาหยิบบ่อยแค่ไหน · บ่อยกว่าลีกกี่เท่า (lift) ·
ตัวนั้นกินพื้นที่เลนเขาเท่าไร

ตัวอย่างจริง (BRU · 120 วันล่าสุด · 20 เกม)

    tamyn     หยิบ 4/20 (20%)  บ่อยกว่าลีก 9.1 เท่า   ป่า
    flowborn  หยิบ 4/20 (20%)  บ่อยกว่าลีก 4.7 เท่า   ADL

ทั้งสองตัวไม่ติด 25 อันดับแรกของลีก การแบนตามเมตารวมจะไม่มีวันแตะ

**บทเรียนเรื่องช่วงเวลา** — ดูข้อมูลทั้งปี BRU มี pool กว้าง 18-24 ตัวต่อเลน
ดูเฉพาะ 120 วันล่าสุดเหลือ 9-11 ตัว ตัวเลขชุดแรกไม่ผิด แต่ตอบคนละคำถาม
`--since` จึงไม่ใช่ของแถม เป็นสิ่งที่ต้องใส่เกือบทุกครั้ง

### 12.4 กติกาที่ยืนยันได้จาก Liquipedia

`configs/draft/format.yaml` เดิมใช้ธง `verified: false` ธงเดียวคลุมทั้งไฟล์
ทั้งที่ในไฟล์มีของสองระดับปนกัน แยกเป็นรายข้อแล้วได้

**ยืนยันแล้ว** — Global Ban-Pick ยกข้อความจากหน้า RoV Pro League/2026/Summer

    "In a Bo3 or Bo5, each team is not allowed to choose the Champions
     they used in the previous rounds (If selecting the opponent's champions
     in the previous game, it is not affected by this rule)"
    "In a Bo7 match, this rule will apply for the first 6 games.
     The 7th game will be returned to the Normal Ban-Pick"

ตรงกับ `scope: own_team_only` · `applies_to_bans: false` · `reset_on_final_game: true` ทุกข้อ

**เจอของใหม่** — Side Selection Privilege ซึ่งยังไม่เคยถูกเข้ารหัสไว้

    เกมแรก ทีมฝั่งซ้ายของตาราง (home) เป็นฝ่ายเลือกข้าง
    เกมถัดไป ทีมที่แพ้เกมก่อนเป็นฝ่ายเลือก

แปลว่าฝั่ง blue/red ไม่ได้สลับอัตโนมัติ — มีผลต่อคำแนะนำระดับซีรีส์

**ยังไม่ยืนยัน** — "ลำดับ" การสลับกันแบนและเลือก ตรวจทั้งหน้า RPL และ GCS
แล้วไม่มีเขียนไว้ ลำดับในไฟล์ยังเป็นรูปแบบมาตรฐานของ MOBA ที่มี 4 ban + 5 pick
ยืนยันได้ด้วยการดูคลิปแข่งหนึ่งคลิปแล้วจดลำดับจริง — ทำได้โดยไม่ต้องรอ vision pipeline
