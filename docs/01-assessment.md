# 01 — ประเมินแผนเดิม และช่องว่างที่ต้องปิด

## 1. สิ่งที่แผนเดิมทำถูกและควรรักษาไว้

| หัวข้อ | ทำไมถึงถูก |
|--------|-----------|
| แยก Observed / Inferred / Unknown (§16, §78) | นี่คือหัวใจ ระบบวิเคราะห์กีฬาส่วนใหญ่พังเพราะเอาค่าที่เดามาปนกับค่าที่วัดได้ |
| แบ่งข้อมูลเป็น 4 Layer และห้ามเขียนทับ Layer ล่าง (§79) | ทำให้เปลี่ยนอัลกอริทึมแล้วประมวลผลย้อนหลังได้ โดยไม่ต้องถอดวิดีโอใหม่ |
| Normalize coordinate เป็น 0..1 (§18) | รองรับ 720p/1080p/1440p ด้วยโค้ดชุดเดียว |
| จำกัด hero ที่ต้องค้นหาเหลือ 10 ตัวจาก draft (§13) | ลดจาก classification 100+ class เหลือ assignment 10 ตัว |
| เริ่มจาก OpenCV ก่อน YOLO (§12) | ถูกต้อง minimap มีพื้นหลังคงที่ ปัญหานี้ไม่จำเป็นต้องใช้ deep learning |
| Draft ผูกกับ patch และเก็บ sample_size (§39, §40) | ป้องกันการรวมสถิติข้าม meta |
| จัดอันดับความเสี่ยงไว้ล่วงหน้า (§77) | ประเมินได้แม่น Identity tracking คือความเสี่ยงอันดับหนึ่งจริง |

## 2. ช่องว่าง 10 ข้อ

เรียงตามผลกระทบ ข้อ G1–G4 ต้องตอบให้ได้ **ก่อนเขียนโค้ดบรรทัดแรก**

---

### G1 · ยังไม่ได้ตอบว่า minimap ใน broadcast มี fog of war หรือไม่ 🔴 บล็อกทุกอย่าง

แผนเดิม §16 และ §78 ตั้งสมมติฐานว่าเห็นศัตรูเฉพาะตอนมี vision
แต่ spectator client มักไม่มี fog — ผู้ชมเห็นครบทั้ง 10 ตัวตลอดเวลา

ผลต่างมหาศาล:

| กรณี | Tracking | ความยาก | Macro ที่ทำได้ |
|------|----------|---------|----------------|
| ไม่มี fog (เห็น 10 ตัวเสมอ) | เป้าหมายคงที่ 10 ตัว assignment ตรงไปตรงมา | ปานกลาง | วิเคราะห์ได้ครบ รวมถึงมุม "ทีมเดินโดยไม่รู้ว่าศัตรูอยู่ไหน" |
| มี fog | จำนวนเป้าหมายผันผวน 5–10 ต้องมีสถานะ UNKNOWN | ยากมาก | ต้องรายงาน coverage ควบคู่ทุกตัวเลข |

**ค้นเว็บแล้วไม่มีคำตอบ** ยืนยันได้เพียงว่า minimap ของ *ผู้เล่น* มี fog
และ fog เปิด/ปิดได้ในการตั้งค่า custom match ไม่มีเอกสารสาธารณะใดระบุพฤติกรรมของ
observer mode ใน AoV รายละเอียดอยู่ใน [08-game-reference.md](08-game-reference.md) §5

ที่สำคัญกว่านั้น: การที่ fog ตั้งค่าได้ในระดับ custom match แปลว่าต้องตรวจ
**ต่อรายการแข่ง** ไม่ใช่ตรวจครั้งเดียวแล้วใช้กับทุกคลิป

**ต้องทำ:** เปิดคลิปจริง หยุดที่นาทีที่สองทีมแยกกันคนละฝั่งแมพ แล้วนับ icon บน minimap
ถ้าได้ 10 ตลอด แปลว่าไม่มี fog และงานง่ายลงมาก
บันทึกคำตอบลง `configs/layouts/<broadcast>.yaml` ที่ฟิลด์ `minimap.fog_of_war`

คำถามคู่กัน: สีของ icon สื่อถึง **ฝ่าย (blue side / red side)** หรือ **มิตร/ศัตรู**
ในมุมมอง spectator ควรเป็นฝ่าย แต่ต้องยืนยันด้วยตา เพราะถ้าเป็นอย่างหลัง
การแยกทีมจากสีจะใช้ไม่ได้เลย

### G2 · ไม่มี Game Clock และการจัดแนวเวลา 🔴

แผนเดิมใช้ `timestamp: 600.5` ซึ่งเป็นเวลาในไฟล์วิดีโอ ใช้จริงไม่ได้ เพราะ

- คลิปมี intro, พิธีกร, หน้า draft, ช่วงพัก ก่อนเกมเริ่ม
- หนึ่งไฟล์อาจมีหลายเกม (BO3/BO5)
- เกมมีการหยุด (pause) จากปัญหาเทคนิค

ถ้าไม่มี game clock จะเทียบข้ามแมตช์ไม่ได้เลย ประโยคอย่าง
"first rotation ที่นาที 1:30" จะไม่มีความหมาย

**ต้องทำ:** OCR นาฬิกาเกมจาก top HUD ทุกเฟรมที่สุ่ม แล้วเก็บสองแกนเวลาคู่กัน

```
video_time  = PTS จากไฟล์   (แกนสำหรับกระโดดดูวิดีโอ)
game_clock  = วินาทีในเกม   (แกนสำหรับวิเคราะห์ทุกอย่าง)
```

`game_clock` ต้องเพิ่มขึ้นทางเดียวภายในหนึ่ง `game_id` ถ้าถอยหลังแปลว่าเป็น replay หรือเกมใหม่

---

### G3 · ไม่มีการจัดการ Replay / Highlight / ภาพตัด 🔴

Broadcast ฉาย replay ของ kill และ teamfight ระหว่างเกม ในช่วง replay:

- minimap แสดงสถานะย้อนหลัง ตำแหน่งจะผิดถ้าเก็บเข้า timeline
- นาฬิกาเดินถอยหลัง
- บาง broadcast ซ่อน minimap หรือใส่ overlay ทับ

ถ้าไม่กรอง ข้อมูล position จะปนเปื้อนแบบเงียบ ๆ และตามหา bug ไม่เจอในภายหลัง

**ต้องทำ:** classifier ระดับเฟรมชื่อ `frame_state` ค่าเป็นหนึ่งใน
`LIVE | REPLAY | PAUSE | DRAFT | NON_GAME`

เกณฑ์ตัดสิน: นาฬิกาถอยหลัง, ไม่พบกรอบ minimap, ตรวจพบ banner/overlay,
perceptual hash ของแถบ HUD เปลี่ยนผิดปกติ

เก็บเฉพาะเฟรม `LIVE` เข้า Layer 2 เฟรมอื่นเก็บไว้ใน Layer 1 พร้อมเหตุผลที่ถูกตัด

---

### G4 · Death/Respawn ควรอ่านจาก HUD ไม่ใช่จาก minimap 🟠

แผนเดิม §30 บอกว่า "Alive → Death → Disappear" คือดูจาก icon หายไป
แต่ icon หายไปได้จากหลายสาเหตุ: ตายจริง, เข้า fog, ถูก icon อื่นบัง, detector พลาด

Side HUD ให้สัญญาณชัดกว่ามาก — portrait จะเป็นสีเทาหรือมีตัวเลขนับถอยหลัง
และ portrait ใน HUD ใหญ่กว่า icon บน minimap หลายเท่า จึงอ่านง่ายกว่ามาก

**ต้องทำ:** อ่านสถานะ alive/dead ต่อ slot จาก HUD เป็นแหล่งหลัก
แล้วใช้เป็น gate ให้ tracker — ตัวที่ตายอยู่ห้ามถูก assign detection ใด ๆ
ตัวนี้ช่วยลด identity switch ได้มากเพราะตัด candidate ผิดออกตั้งแต่ต้นทาง

---

### G5 · Detector ยังไม่ได้ใช้ประโยชน์จากพื้นหลังที่คงที่ 🟠

แผนเดิม §12 เสนอ color segmentation + contour + template matching
วิธีที่แรงกว่าและง่ายกว่าคือ **median background subtraction**

ภูมิประเทศบน minimap (ป่า แม่น้ำ เลน ป้อม) นิ่งสนิทตลอดเกม
สร้างภาพพื้นหลังจาก median ของเฟรมสุ่ม 200–500 เฟรม แล้วลบออก
สิ่งที่เหลือคือของที่เคลื่อนไหว ได้แก่ hero icon, minion, ping, marker

วิธีนี้จัดการกรณีที่ color threshold แก้ไม่ได้ เช่น icon สีน้ำเงินทับพื้นที่แม่น้ำสีน้ำเงิน

---

### G6 · Hero identification เป็นปัญหา Assignment ไม่ใช่ Classification 🟠

แผนเดิม §13 คิดในกรอบ "สร้าง template 10 ตัว แล้วค้นหาทีละตัว"
แต่ icon บน minimap ที่ความละเอียด 720p มีขนาดราว 16–22 px
รายละเอียดของ portrait แทบไม่เหลือ template matching เดี่ยว ๆ
จะสับสนระหว่างฮีโร่ที่โทนสีใกล้กันอย่างแน่นอน

กรอบที่ถูกคือ: ในแต่ละเฟรมเรามี detection N จุด และ track ที่รู้จัก 10 อัน
แก้เป็น **bipartite assignment (Hungarian)** โดยต้นทุนรวมสามอย่าง

```
cost = w_d · ระยะจากตำแหน่งที่ทำนายไว้
     + w_a · (1 − ความคล้ายของ patch)
     + w_s · โทษจากข้อจำกัด (ตายอยู่ / เกินความเร็วสูงสุด / ผิดฝ่าย)
```

appearance เป็นเพียงหนึ่งในสัญญาณ ไม่ใช่ตัวตัดสิน
สิ่งที่ทำให้ระบบแม่นจริงคือข้อจำกัดเชิงโครงสร้าง:
หนึ่งทีมมีได้ไม่เกิน 5 ตัว และหนึ่ง track จับคู่ detection ได้ไม่เกิน 1 จุด

---

### G7 · Draft Engine ไม่มีข้อมูลตั้งต้น (Cold Start) 🟠

แผนเดิม §36–§41 ออกแบบรอบตาราง `hero_matchups` และ `hero_synergies` ที่มีตัวเลขอยู่แล้ว
แต่วันแรกตารางเหล่านี้ว่างเปล่า และต้องใช้แมตช์หลักร้อยกว่าจะมีความหมายทางสถิติ

ทางออกคือแยก Draft เป็นสองรุ่นให้ชัด

| รุ่น | ใช้ข้อมูลอะไร | ต้องมีกี่แมตช์ | ให้อะไรได้ |
|------|---------------|----------------|------------|
| Draft v1 | hero attribute ที่คนกรอกเอง (role, damage type, engage, CC, scaling, mobility, range) | 0 | Role balance, damage mix, engage/peel, power curve, ช่องโหว่ของทีม |
| Draft v2 | matchup/synergy เชิงประจักษ์ + shrinkage | 200+ | counter score, win probability |

Draft v1 มีประโยชน์จริงและทำได้ทันทีโดยไม่ต้องรอ vision เสร็จ
ควรทำก่อน และควรทำขนานไปกับงาน CV เพราะไม่แย่งทรัพยากรกัน

**อัปเดตหลังค้นข้อมูล:** Cold start แก้ได้เร็วกว่าที่คิด
Liquipedia API ให้ข้อมูล draft order (pick และ ban) ต่อแมตช์ ย้อนหลังถึงปี 2021
จึงไม่ต้องกรอกมือ 200 แมตช์ตามที่เขียนไว้เดิม
เขียน importer แทน ใช้เวลาราว 2 วัน แล้วรันดึงข้ามคืน
Draft v2 จึงเริ่มได้เร็วกว่าแผนเดิมมาก ดู [08-game-reference.md](08-game-reference.md) §8

ข้อจำกัดที่ต้องเคารพ: 60 requests/ชั่วโมง และ 1 request/2 วินาที
ละเมิดแล้วโดนแบน IP ต้อง cache ทุก response ลงดิสก์และห้ามยิงซ้ำ

### G8 · Win rate ดิบใช้ไม่ได้ ต้องมี Shrinkage 🟡

แผนเดิม §39 เก็บ `sample_size` ไว้ถูกแล้ว แต่ไม่ได้ระบุวิธีใช้
ถ้าไม่จัดการ ฮีโร่ที่เจอกัน 3 ครั้งชนะ 3 จะได้ 100% และขึ้นอันดับหนึ่งตลอดกาล

ใช้ Beta-Binomial shrinkage ดึงเข้าหาค่ากลาง

```
wr_adj = (wins + k · prior) / (games + k)

prior = win rate ของฮีโร่ตัวนั้นใน patch เดียวกัน  (ไม่ใช่ 0.5)
k     = 20–50  ปรับด้วย cross-validation
```

และแสดง confidence interval ควบคู่บน UI เสมอ ไม่ใช่แสดงตัวเลขเดียวโดด ๆ

---

### G9 · ไม่มี Evaluation Harness ตั้งแต่วันแรก 🟡

แผนเดิม §73–§75 ระบุ metric ไว้ครบ แต่วางไว้ช่วงท้าย
ถ้าไม่มีเครื่องมือวัดตั้งแต่วันแรก จะไม่มีทางรู้ว่าการปรับ threshold ทำให้ดีขึ้นหรือแย่ลง
และจะเสียเวลาไปกับการปรับค่าแบบเดา

**ต้องทำก่อนเขียน detector:**

1. กำหนดรูปแบบไฟล์ ground truth
2. เขียนคำสั่ง `rov eval detect --match M001` ที่พิมพ์ precision / recall / MAE
3. label ด้วยมือ 100 เฟรมจาก 1 แมตช์

100 เฟรมเพียงพอต่อการตัดสินใจแล้ว และใช้เวลา label ราว 2 ชั่วโมง

---

### G10 · Confidence ต้องถูก Calibrate ไม่ใช่แค่ให้คะแนน 🟡

แผนเดิมใส่ `confidence: 0.87` ในหลายที่ ซึ่งเป็นทิศทางที่ดี
แต่ต้องนิยามให้ชัดว่าเลขนี้แปลว่าอะไร

กฎ: ถ้าเหตุการณ์ที่ระบบให้ confidence 0.8 ถูกต้องจริงราว 80% ถือว่า calibrated
วัดด้วย reliability diagram เทียบกับ ground truth เป็นระยะ

ถ้ายัง calibrate ไม่ได้ ให้ใช้ป้ายหยาบ `HIGH / MEDIUM / LOW` แทนตัวเลขทศนิยม
ตัวเลขทศนิยมที่ไม่ได้ผ่านการวัดอันตรายกว่าป้ายหยาบที่ซื่อสัตย์

## 3. สิ่งที่ควรตัดออกจากขอบเขตช่วงต้น

| ตัดออก | เหตุผล | เอากลับมาเมื่อ |
|--------|--------|----------------|
| Supabase / cloud storage | เพิ่มความซับซ้อนโดยไม่ช่วยงาน CV เลย เริ่มด้วย Postgres local + ไฟล์บนดิสก์ | มีผู้ใช้มากกว่า 1 คน |
| Next.js dashboard | Phase 1–3 ตรวจงานด้วยภาพ overlay และ CSV ได้หมด | ผ่าน Milestone 3 |
| WebSocket / realtime | Polling ทุก 2 วินาทีพอสำหรับ job ที่ใช้เวลาเป็นนาที | มีผู้ใช้จริงบ่นเรื่อง UX |
| YOLO / PyTorch | ยังไม่รู้ว่า classical CV ไม่พอ อย่าซื้อความซับซ้อนล่วงหน้า | classical CV แตะเพดานที่วัดได้แล้ว |
| Teamfight detection จาก main view | ต้องแก้ปัญหา CV อีกชุดที่ยากพอกับ minimap | Milestone 4 และทำจาก minimap + HUD ให้ได้ก่อน |
| Celery / Redis | ตาราง `jobs` + worker process เดียวพอสำหรับเครื่องเดียว | ต้องมี worker มากกว่า 1 เครื่อง |

## 4. คำถาม Phase 0 ที่ต้องมีคำตอบก่อนเริ่ม

ทั้งหมดตอบได้ด้วยการเปิดคลิปจริงและวัด ใช้เวลารวมไม่เกินครึ่งวัน

1. minimap แสดงครบ 10 ตัวเสมอหรือไม่ (G1)
2. สี icon สื่อถึงฝ่าย หรือ มิตร/ศัตรู
3. minimap ROI อยู่พิกัดใดที่ 720p และคงที่ตลอดคลิปหรือไม่
4. icon มีเส้นผ่านศูนย์กลางกี่ pixel
5. minimap เป็นสี่เหลี่ยมจัตุรัสตรง หรือถูกบิดมุม (ต้องใช้ homography หรือ affine พอ)
6. นาฬิกาเกมอยู่ตำแหน่งใด และ OCR อ่านได้หรือไม่
7. HUD บอกสถานะตายอย่างไร (portrait เทา / ตัวเลขนับถอยหลัง)
8. มี replay ระหว่างเกมบ่อยแค่ไหน และมี banner บอกหรือไม่
9. ระหว่าง teamfight icon ทับกันจนนับไม่ได้คิดเป็นกี่เปอร์เซ็นต์ของเวลา
10. ping และ marker อื่นบน minimap หน้าตาเป็นอย่างไร (ต้องกรองออก)
11. mark ของ Dragon และ Slayer อยู่พิกัดใดบน minimap และสีเหลือง/เทาต่างกันชัดแค่ไหน
12. เวลาเกิดของ Dragon และ Slayer ตรงกับตารางใน [08-game-reference.md](08-game-reference.md) §3 หรือไม่
    (แพตช์ 26 มิ.ย. 2026 แก้ระบบ jungle จึงต้องวัดซ้ำ)

ผลลัพธ์ของ Phase 0 คือสองไฟล์: `configs/layouts/<broadcast>.yaml`
และ `configs/params/objectives.yaml`
