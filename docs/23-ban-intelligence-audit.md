## 1. candidate pool ถูกสร้างอย่างไร

```python
legal = state.legal_moves()
if is_ban:
    legal = legal - state.locked_by_series(subject)     # subject = ศัตรู
candidates = [h for h in legal if stats.get(h).picks >= min_games]
```

| | ตอน pick | ตอน ban |
|---|---|---|
| ตัดตัวที่ถูกเลือก/แบนไปแล้ว | ✓ | ✓ |
| ตัดตัวที่ **ทีมตัวเอง** ใช้ไม่ได้ (Global Ban-Pick) | ✓ | — |
| ตัดตัวที่ **ศัตรู** ใช้ไม่ได้ | — | ✓ |
| กรอง `picks >= min_games` | ✓ | ✓ |

**ส่วนนี้ถูกต้องแล้ว** — การไม่เสียตาแบนกับตัวที่ศัตรูหยิบไม่ได้อยู่แล้ว
เป็นตรรกะที่ถูกต้องและเป็นสิ่งที่ baseline ทั้งสามตัวไม่มี

## 2–3. team context กับ opponent context

```python
subject = team.opponent if is_ban else team
ours    = state.picks(subject)             # ตอนแบน = ตัวที่ "ศัตรู" เปิดแล้ว
theirs  = state.picks(subject.opponent)    # ตอนแบน = ตัวที่ "เรา" เปิดแล้ว
```

การสลับมุมนี้**ถูกต้องตามนิยามของการแบน** — เราอยากรู้ว่าตัวนี้ดีต่อศัตรูแค่ไหน

| ตัวแปร | ตอน pick | ตอน ban |
|---|---|---|
| `ours` | ทีมเรา | **ทีมศัตรู** |
| `theirs` | ทีมศัตรู | **ทีมเรา** |

## 4. role_fit ถูกคำนวณอย่างไร — และทำไมมันไม่ใช่ปัญหา

```python
need = needed_lanes(ours, lu, ln_all)      # เลนที่ "ศัตรู" ยังไม่เปิด
fit  = role_fit(hid, need, lu, ln_all) if need else 1.0
total = base * (ROLE_FLOOR + (1 - ROLE_FLOOR) * fit)
```

```python
def role_fit(hero, need, lane_usage, lanes):
    if not usage or not need or len(need) == len(lanes):
        return 1.0          # ← ทางออกนี้ทำงานที่ตาแบนแรกทุกครั้ง
```

**ผลจากการ trace จริง (ตาที่ 1 · blue ban)**

```
need = ['dragon', 'ds', 'jungle', 'mid', 'support']   ครบ 5 เลน
role_fit ของทุก candidate = 1.00
```

เมื่อศัตรูยังไม่เปิดตัวเลย `need` จึงเท่ากับเลนทั้งหมด และ `role_fit` คืน 1.0
ให้ทุกตัวเหมือนกันหมด — **เป็นกลางสนิท ไม่ได้บิดเบือนอันดับแม้แต่นิดเดียว**

ที่ตาแบนเฟส 2 `need` กลายเป็นเซ็ตย่อยจริง และ `role_fit` เริ่มมีผล
ซึ่ง**ก็ยังถูกต้อง** — แบนเมจตัวที่สองใส่ทีมที่มีเมจแล้วคือแบนทิ้งเปล่า

**สรุป: `role_fit` ใช้มุมมองถูกต้องแล้วทั้งสองเฟส ไม่ต้องแก้**

## 5. counter / synergy ใช้มุมมองใคร

```python
counter = _counter_against(pooled, hid, theirs, prior)   # vs ตัวที่ "เรา" เปิด
synergy = _synergy_with(pooled, hid, ours, prior)        # กับตัวที่ "ศัตรู" เปิด
```

ตอนแบน ทั้งคู่แปลว่า

- `counter` = ถ้าศัตรูได้ตัวนี้ มันจะกดทีมเราแค่ไหน → **ตรงกับนิยามการแบน** ✓
- `synergy` = ถ้าศัตรูได้ตัวนี้ มันจะเข้ากับคอมพ์เขาแค่ไหน → **ตรงเช่นกัน** ✓

**มุมมองถูกต้องทั้งคู่** แต่ที่ตาแบนเฟส 1 ทั้งคู่ตาย เพราะยังไม่มีใครเปิดตัว

```
counter = 50.0 ทุกตัว   (raw = 0 · "ศัตรูยังไม่ได้เลือก")
synergy = 50.0 ทุกตัว   (raw = 0 · "ทีมยังไม่ได้เลือก")
```

รวมกันเป็นค่าคงที่ `0.08×50 + 0.05×50 = 6.5` แต้มบวกให้ทุก candidate เท่ากัน —
ไม่บิดเบือนอันดับ แต่ก็ไม่ช่วยอะไรเลย

### ทำไม win rate ถึงไม่เหมาะกับการแบน

1. **win rate ระดับอาชีพเกาะ 50% โดยโครงสร้าง** ทุกเกมมีผู้ชนะหนึ่งฝ่าย
   ความต่างระหว่างตัวบนกับตัวล่างจึงแคบและไวต่อ noise
   [docs/22](22-benchmark-foundation.md) วัดไว้: Baseline B (win rate ล้วน)
   ได้ `0.007` บนตาแบน ขณะที่ Baseline A (presence ล้วน) ได้ `0.265`
2. **การแบนไม่ได้ถามว่า "ตัวนี้ชนะบ่อยไหม"** แต่ถามว่า **"ถ้าปล่อยไป จะเจ็บแค่ไหน"**
   ซึ่งขึ้นกับ *ความน่าจะเป็นที่ศัตรูจะหยิบ* คูณกับ *ความแรงของมัน*
   `presence` วัดตัวแรกโดยตรง — และตัวแรกเป็นตัวคูณของทุกอย่าง
3. **`weights_for()` ถูกออกแบบมาเพื่อ pick** docstring ของมันเขียนไว้ตรง ๆ ว่า
   เจตนาคือ "ต้นดราฟต์ยังไม่มีใครเปิดตัว จึงเหลือแต่ meta กับ win rate"
   ซึ่งเป็นเหตุผลที่ใช้ได้กับการเลือก แต่ไม่ใช่กับการแบน

## 7. สรุปสาเหตุ

| องค์ประกอบ | มุมมอง | สถานะ |
|---|---|---|
| candidate pool | ตัดตัวที่ศัตรูใช้ไม่ได้ | ✅ ถูกต้อง |
| `ours` / `theirs` สลับมุม | ศัตรูเป็น subject | ✅ ถูกต้อง |
| `role_fit` | เลนที่ศัตรูยังว่าง | ✅ ถูกต้อง · เป็นกลางที่เฟส 1 |
| `counter` | candidate vs ทีมเรา | ✅ ถูกต้อง · ตายที่เฟส 1 |
| `synergy` | candidate กับทีมศัตรู | ✅ ถูกต้อง · ตายที่เฟส 1 |
| **`weights_for()`** | **ใช้โปรไฟล์ของ pick** | 🔴 **ไม่เหมาะกับ ban** |
| **`winrate`** | **น้ำหนักมากกว่า meta** | 🔴 **สัญญาณเกือบเป็น noise สำหรับ ban** |

**สาเหตุเดียว: โปรไฟล์น้ำหนัก ไม่ใช่มุมมอง ไม่ใช่โครงสร้าง**

ทุกมุมมองใน ban path ถูกต้องหมดแล้ว สิ่งเดียวที่ผิดคือการเอา
โปรไฟล์น้ำหนักของโจทย์ "เลือก" ไปใช้กับโจทย์ "แบน" ซึ่งเป็นคนละโจทย์

## 8. สิ่งที่ audit นี้ **ไม่** พบ

เขียนไว้เพื่อกันการแก้เกินจำเป็น

- ❌ ไม่พบว่า `role_fit` ใช้มุมมองผิด
- ❌ ไม่พบว่า counter/synergy สลับข้าง
- ❌ ไม่พบบั๊กในการสร้าง candidate pool
- ❌ ไม่พบว่าต้องเขียน Ban Engine ใหม่

**minimal fix จึงควรแตะแค่โปรไฟล์น้ำหนักของตาแบน** และไม่แตะ pick path เลย
