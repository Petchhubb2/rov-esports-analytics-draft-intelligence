# 25 — Ban Benchmark

PHASE M0.75 · STEP 5–9 · วัดเมื่อ 2026-09-11

**holdout รันครั้งเดียวหลังตัดสินใจเสร็จ ตามกติกาที่ประกาศไว้ใน [docs/24 §7](24-ban-intelligence-spec.md)**

---

## 1. Root cause

[docs/23](23-ban-intelligence-audit.md) trace ban path ทั้งเส้นแล้วพบว่า
**ทุกมุมมองถูกต้องอยู่แล้ว** — candidate pool, การสลับ subject เป็นศัตรู,
`role_fit`, ทิศทางของ counter/synergy

สาเหตุเดียวคือ **`weights_for()` เป็นโปรไฟล์ของโจทย์ "เลือก" แต่ถูกใช้กับโจทย์ "แบน"**

```
weights_for(0, 0)   meta 0.392   winrate 0.479   ← winrate มากกว่า meta
```

ผลคือตาแบนแรกถูกตัดสินด้วย win rate เป็นหลัก ซึ่งระดับอาชีพเกาะ 50%
โดยโครงสร้างและเป็น noise เกือบล้วนบนตัวอย่างเล็ก

หลักฐานจาก trace ตาที่ 1

```
annette   presence 22%  wr scaled  96.3  → อันดับ 4
astrid    presence 13%  wr scaled 100.0  → อันดับ 6
elandorr  presence 72%  wr 0.477         → ไม่ติด 6 อันดับแรก
```

> ⚠️ [docs/22 §4](22-benchmark-foundation.md) เคยเขียนว่าสาเหตุคือ `role_fit`
> **ข้อความนั้นผิด** — `role_fit` คืน 1.0 ให้ทุกตัวที่ตาแบนแรก จึงเป็นกลางสนิท
> ได้แก้ไว้ใน docs/23 แล้ว บทเรียน: ต้อง trace ก่อนเขียนสาเหตุลงเอกสาร

## 2. Minimal fix

เพิ่มฟังก์ชันเดียว `ban_weights_for()` ที่ใช้โครงสร้างของ `weights_for()` ทุกอย่าง
ต่างแค่การแบ่ง `rest` ระหว่าง meta กับ winrate

```python
PICK_META_SHARE = 0.45      # เดิม · ไม่แตะ
BAN_META_SHARE  = 0.75      # ใหม่

profile = ban_weights_for if is_ban else weights_for   # ★ จุดเดียวที่แยกทาง
```

| | pick | ban |
|---|---|---|
| meta / winrate ของ `rest` | 0.45 / 0.55 | **0.75 / 0.25** |
| การไหลของ counter | `0.08 + 0.40e` | **เหมือนเดิม** |
| การไหลของ synergy | `0.05 + 0.25a` | **เหมือนเดิม** |
| ผลรวมน้ำหนัก | 1.0 | **1.0 (เท่ากัน)** |

**สิ่งที่ไม่ได้แตะ:** `weights_for()` · `role_fit` · perspective · candidate pool ·
ไม่เพิ่ม component ใหม่ · ไม่สร้าง Ban Engine แยก

ที่มาของ 0.75/0.25 เป็นการตัดสินใจเชิงโครงสร้าง (`BanPriority ≈ P × Harm`
โดย meta ประมาณ `P` ซึ่งเป็นตัวคูณ) ประกาศไว้ใน docs/24 **ก่อนวัดผล**
และ**ไม่ได้ลองค่าอื่น**

## 3. การแบ่งข้อมูล

```
validation setup   train ...–2026-02-28 (397 เกม) · eval 2026-03-01–2026-05-08
holdout setup      train ...–2026-05-08 (719 เกม) · eval 2026-05-09–2026-09-06
```

**ใช้ train ของ holdout ให้ตรงกับ [docs/22](22-benchmark-foundation.md)** เพื่อให้
ตัวเลขก่อน/หลังเทียบกันได้ตรง ๆ · แบ่งตามเวลาทั้งคู่ ไม่สุ่ม

ทุก ranker ถูกวัดบน**ตาชุดเดียวกันในการรันครั้งเดียว** รวมถึง `D · engine ก่อนแก้`
ซึ่งจำลองพฤติกรรมเดิมโดยบังคับให้ตาแบนใช้โปรไฟล์ของ pick

หลักฐานว่า D จำลองถูก: D บน holdout ban ได้ `0.023` ซึ่ง**ตรงกับตัวเลขใน docs/22 เป๊ะ**

|---|---|---|---|---|
| **D · engine ก่อนแก้** | **0.023** | 0.334 | 0.218 | 19.75 |
| **current engine (หลังแก้)** | **0.268** | 0.351 | **0.354** | **15.49** |
| A · presence | 0.265 | **0.387** | 0.366 | **12.09** |
| C · role + presence | 0.265 | 0.368 | 0.352 | 16.17 |
| B · win rate | 0.007 | 0.046 | 0.097 | 29.61 |

**ดีขึ้นทุกตัวชี้วัด** — top-1 `+0.245` · MRR `+0.136` · mean rank ดีขึ้น 4.3 อันดับ

ช่วงความเชื่อมั่น 95% (Wilson)

```
ก่อนแก้   0.023  [0.011, 0.047]
หลังแก้   0.268  [0.221, 0.321]      ต่างอย่างมีนัย
```

engine ตอนนี้**เสมอกับ presence baseline** บน top-1 (ไม่ได้ชนะอย่างมีนัย
แต่ไม่แพ้แล้ว) และยังตามหลัง A อยู่บน top-3 กับ mean rank

## 8. Remaining uncertainty

1. **ส่วนต่างระหว่างสองหน้าต่างห่างกันมาก**
   holdout `+0.245` แต่ validation `+0.021` — ยังไม่รู้แน่ว่าทำไม
   ข้อสังเกต: ทุก ranker ทำได้แย่กว่าบน validation (A ได้ 0.156 vs 0.265)
   น่าจะเพราะ train เล็กกว่า (397 vs 719 เกม) ทำให้ presence ประมาณได้แย่ลง
   **แต่ยังไม่ได้พิสูจน์** — ควรทดสอบด้วยการ fix train size แล้วเลื่อนหน้าต่าง
2. **validation ไม่ยืนยันการปรับปรุงทางสถิติ** ช่วงความเชื่อมั่นทับกัน
   ข้อสรุปว่า "ดีขึ้น" จึงพิงกับ holdout เป็นหลัก ซึ่งรันครั้งเดียวตามกติกา
   การมีสองหน้าต่างที่ชี้ทางเดียวกันช่วยได้ แต่ไม่เท่ากับการยืนยันสองครั้ง
3. **engine ยังตามหลัง A บน top-3 และ mean rank** (0.351 vs 0.387 · 15.5 vs 12.1)
   แปลว่ายังมีหางที่ engine จัดอันดับพลาดหนักกว่า presence ล้วน
4. **0.75/0.25 ไม่ใช่ค่าที่ optimal** เป็นค่าที่เลือกจากเหตุผลเชิงโครงสร้าง
   ไม่ได้ค้นหา และ**จะไม่ค้นหาในเฟสนี้** การหาค่าที่ดีที่สุดต้องมีหน้าต่างใหม่
   ที่ยังไม่เคยดู ซึ่งตอนนี้ใช้หมดแล้วทั้ง validation และ holdout
5. **ยังไม่ได้แตะ Flex Denial กับ Enabler Prevention** ซึ่ง docs/24 §2 ระบุว่า
   เป็น feature ของ BanPriority ที่ยังขาด — เป็นงานของ M1 ขึ้นไป
6. **top-1 ยังวัด "ตรงกับทีมอาชีพ" ไม่ใช่ "ถูกต้อง"** ข้อจำกัดเดิมจาก docs/22 §7
   การที่ engine เข้าใกล้ presence baseline อาจแปลว่ามัน**เลียนแบบ**ได้ดีขึ้น
   ไม่ใช่ว่ามัน**แบนเก่งขึ้น** — สองอย่างนี้แยกกันไม่ได้ด้วยข้อมูลที่มี
