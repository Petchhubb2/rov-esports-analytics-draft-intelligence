# 14 — จากเครื่องตัวเอง ไปเซิร์ฟเวอร์จริง

เอกสารนี้ตอบคำถามว่า ถ้าจะเอาระบบขึ้นเซิร์ฟเวอร์จริง ต้องเตรียมอะไร
และมีอะไรที่ **ห้ามยกขึ้นไปตรง ๆ**

---

## 1. ตอนนี้อยู่ตรงไหน

```
เครื่องตัวเอง
├── PostgreSQL 18.6          ← Scheduled Task เปิดตอน logon
├── rov CLI                  ← งานทั้งหมดของ vision และ draft
├── FastAPI (apps/api)       ← System 01 เท่านั้น ยังไม่ได้รันเป็น service
└── หน้าเว็บ draft           ← ไฟล์เดียว เปิดจากดิสก์ได้เลย
```

รันหน้าเว็บในเครื่อง

```bash
python scripts/export_draft_data.py    # สถิติ -> JSON
python scripts/build_draft_page.py     # JSON + รูป -> HTML
rov web                                # เปิดที่ http://127.0.0.1:8000
```

## 2. เรื่องที่ต้องตัดสินใจก่อน ไม่ใช่เรื่องเทคนิค

### 2.1 ลิขสิทธิ์ภาพฮีโร่ 🔴

นี่คือเรื่องที่ต้องเคลียร์ก่อนขึ้นเว็บสาธารณะ

| สิ่งที่ใช้ | เจ้าของ | สัญญาอนุญาต |
|-----------|---------|-------------|
| ข้อมูล draft (pick/ban/ผล) | Liquipedia | CC-BY-SA 3.0 · **ต้องให้เครดิต** |
| ภาพฮีโร่ | **Garena / TiMi Studios** | ลิขสิทธิ์ของผู้พัฒนาเกม |
| ผังโซนที่ระบบวาดเอง | เรา | ไม่มีปัญหา |

Liquipedia โฮสต์ภาพฮีโร่ในฐานะสื่อประกอบ ไม่ได้เป็นเจ้าของ
สัญญา CC-BY-SA ของ Liquipedia **ไม่ครอบคลุมภาพเหล่านี้**

| การใช้งาน | ความเห็น |
|-----------|----------|
| ในเครื่อง / ในทีมตัวเอง | เป็นแนวปฏิบัติปกติของเครื่องมือวิเคราะห์ |
| ทำ template ให้ CV | เป็นการประมวลผลภายใน ไม่ได้เผยแพร่ซ้ำ |
| เว็บสาธารณะ / เชิงพาณิชย์ | **ต้องขออนุญาต หรือไม่ใช้ภาพ** |

**ทางเลือกถ้าจะขึ้นสาธารณะ**

1. ขออนุญาตจาก Garena Thailand โดยตรง
2. ไม่ใช้ภาพเลย ใช้ชื่อฮีโร่กับสีตาม class แทน (หน้าเว็บรองรับอยู่แล้ว
   ถ้าไม่มีโฟลเดอร์ `assets/heroes` ช่องรูปจะว่างไว้เฉย ๆ ไม่พัง)
3. จำกัดการเข้าถึงไว้เฉพาะคนในทีม ไม่เปิดสาธารณะ

ระบบออกแบบให้ **แยกภาพออกจากโค้ดและข้อมูล** อยู่แล้ว
`data/assets/` ถูก gitignore ไว้ และหน้าเว็บอ้างรูปแบบ path ไม่ได้ฝังลงไฟล์
จึงเลือกได้ทีหลังโดยไม่ต้องแก้อะไร

### 2.2 เครดิต Liquipedia

CC-BY-SA บังคับให้ให้เครดิต ต้องมีข้อความประมาณนี้บนหน้าเว็บ

> ข้อมูลการแข่งขันจาก [Liquipedia](https://liquipedia.net/honorofkings)
> ภายใต้สัญญาอนุญาต CC-BY-SA 3.0

ตอนนี้หน้าเว็บบอกชื่อรายการแข่งแล้ว แต่**ยังไม่ได้ใส่ข้อความสัญญาอนุญาต**
ต้องเพิ่มก่อนเผยแพร่

### 2.3 ข้อมูลวิดีโอการแข่งขัน

คลิปแข่งเป็นลิขสิทธิ์ของผู้จัด ระบบเก็บแค่ **ตัวเลขตำแหน่ง** ที่สกัดออกมา
ไม่ได้เก็บวิดีโอ ซึ่งเป็นการออกแบบที่ปลอดภัยกว่า
แต่ถ้าจะทำฟีเจอร์ "กด event แล้ววิดีโอกระโดดไป" ต้องคิดเรื่องนี้ใหม่
เพราะต้องมีวิดีโอให้เล่น

## 3. สิ่งที่ต้องแก้ทางเทคนิค

### 3.1 ที่พร้อมแล้ว

| ส่วน | สถานะ |
|------|-------|
| ตรรกะทั้งหมดอยู่ใน package เดียว ไม่ผูกกับ web | ✅ ยกไปที่ไหนก็ได้ |
| `DATABASE_URL` อ่านจาก environment | ✅ ไม่ต้องแก้โค้ด |
| คิวงานใช้ตาราง + SKIP LOCKED | ✅ รองรับหลาย worker |
| API แยกจากการประมวลผล | ✅ ตาม Blueprint §56 |

### 3.2 ที่ยังขาด

| ต้องทำ | ทำไม |
|--------|------|
| **Authentication** | ตอนนี้ใครเข้าถึง API ก็ลบแมตช์ได้ |
| **Alembic migration** | ตอนนี้ใช้ `create_all` ซึ่งใช้บน production ไม่ได้ |
| **CORS + rate limit** | API ยังเปิดหมด |
| **จำกัดขนาดไฟล์อัปโหลด** | มี 8 GB แต่ยังไม่มีโควตาต่อผู้ใช้ |
| **HTTPS + reverse proxy** | uvicorn ไม่ควรรับ traffic ตรง |
| **แยก storage ของวิดีโอ** | ไฟล์หลาย GB ไม่ควรอยู่บนดิสก์เดียวกับ DB |
| **Secret management** | ยังไม่มี secret แต่จะมีเมื่อมี auth |

### 3.3 รูปที่แนะนำ

```
                    ┌─────────────┐
   ผู้ใช้ ─ HTTPS ─▶ │  Caddy      │  จัดการใบรับรอง + reverse proxy
                    └──────┬──────┘
                ┌──────────┴──────────┐
                ▼                     ▼
        ┌───────────────┐     ┌──────────────┐
        │ หน้าเว็บ static │     │  FastAPI     │
        │ draft board    │     │  (uvicorn)   │
        └───────────────┘     └──────┬───────┘
                                     │
                       ┌─────────────┼─────────────┐
                       ▼             ▼             ▼
                ┌───────────┐ ┌───────────┐ ┌───────────┐
                │PostgreSQL │ │  worker   │ │  storage  │
                │           │ │ (vision)  │ │  วิดีโอ    │
                └───────────┘ └───────────┘ └───────────┘
```

**worker ต้องแยกเครื่องหรืออย่างน้อยแยก process** เพราะการ decode วิดีโอ
กิน CPU เต็มแกน ถ้ารันร่วมกับ API จะทำให้ API ตอบช้าไปด้วย

### 3.4 ขนาดเครื่องที่ต้องใช้

จากที่วัดได้ในเครื่อง (docs/09 §8)

| งาน | ทรัพยากร |
|-----|----------|
| หน้าเว็บ draft | static ล้วน · เครื่องเล็กสุดก็พอ |
| API + DB | 2 vCPU · 4 GB · ดิสก์ 20 GB |
| worker วิเคราะห์วิดีโอ | 4 vCPU ขึ้นไป · 8 GB · ดิสก์เท่าขนาดคลิปที่เก็บ |
| ยังไม่ต้องใช้ GPU | Milestone 1-4 ใช้ classical CV ล้วน |

## 4. ลำดับที่แนะนำ

ยกขึ้นทีละชั้น ไม่ต้องยกทั้งหมดพร้อมกัน

| ขั้น | ยกอะไร | ได้อะไร | ต้องเคลียร์อะไรก่อน |
|-----|--------|---------|---------------------|
| 1 | หน้าเว็บ draft อย่างเดียว (static) | ทีมใช้ดราฟต์ได้จากทุกเครื่อง | เครดิต Liquipedia · ตัดสินใจเรื่องภาพ |
| 2 | + API + PostgreSQL | เก็บข้อมูลรวมศูนย์ | auth · migration |
| 3 | + worker วิเคราะห์วิดีโอ | อัปโหลดคลิปแล้ววิเคราะห์ | storage · ผ่าน Milestone 3 ก่อน |
| 4 | + dashboard เต็ม | ครบตาม Blueprint | ทุกอย่างข้างบน |

**ขั้นที่ 1 ทำได้ทันที** เพราะหน้าเว็บเป็น static ไฟล์เดียว
เอาขึ้น Netlify, Cloudflare Pages หรือ GitHub Pages ก็ได้ ไม่ต้องมีเซิร์ฟเวอร์

**อย่าข้ามไปขั้นที่ 3 ก่อนผ่าน Milestone 3** เพราะ tracking ยังไม่มีเลย
การยกเครื่องที่ยังทำงานไม่ได้ขึ้นเซิร์ฟเวอร์ ไม่ได้ทำให้มันทำงานได้

## 5. ก่อนกดขึ้นจริง

```
□ ตัดสินใจเรื่องภาพฮีโร่ (ข้อ 2.1)
□ ใส่ข้อความเครดิต Liquipedia CC-BY-SA บนหน้าเว็บ
□ ตั้ง ROV_DATABASE_URL ผ่าน environment ไม่ใช่ในโค้ด
□ เปลี่ยนจาก create_all เป็น alembic
□ ใส่ authentication ก่อนเปิด API สู่ภายนอก
□ ตั้ง backup ของ PostgreSQL
□ จำกัด CORS ให้เฉพาะโดเมนของเรา
□ ตรวจว่า data/ ไม่ได้หลุดเข้า git (ตอนนี้ gitignore ไว้แล้ว)
```
