PHASE M0.5 · วัดเมื่อ 2026-09-11 · **ไม่แก้น้ำหนัก ไม่เปิด factor ไม่นำ knowledge ใหม่เข้า**

เป้าหมายเดียว: ตอบคำถามที่ [docs/21 §8](21-phase-b-report.md) ข้อ 3 ค้างไว้ —
*"ระบบปัจจุบันเก่งกว่าการเลือกแบบ baseline จริงหรือไม่"*

> **คำตอบสั้น:** ยังไม่ — โดยรวม engine **แพ้** baseline ที่ง่ายที่สุดอย่างมีนัยสำคัญ
> แต่เมื่อแยก ban ออกจาก pick แล้วพบว่าปัญหาอยู่ที่ **การแบน** ทั้งหมด
> ส่วนการ **เลือก** engine นำอยู่ แม้จะยังไม่ถึงระดับที่พูดได้ว่ามีนัยสำคัญ

**แบ่งตามเวลา ไม่ใช่สุ่ม** (ข้อ 2 ของ PHASE M0.5) เพราะเมตาเปลี่ยนตามเวลา

## 4. ข้อค้นพบหลัก — ban กับ pick เป็นคนละเรื่อง

| ประเภทตา | n | engine | A | B | C |
|---|---|---|---|---|---|
| **ban** | 302 | **0.023** | 0.265 | 0.007 | 0.265 |
| **pick** | 174 | **0.115** | 0.075 | 0.011 | 0.109 |

**ผลรวมที่ engine แพ้ มาจากตาแบนล้วน ๆ** — ตาแบนคิดเป็น 63% ของตาที่นับคะแนน
และ engine ทำได้แย่กว่า baseline ถึง 11 เท่าในส่วนนั้น

### ทำไม engine ถึงแย่เรื่องแบนขนาดนี้

`recommend()` ตอนแบน **กลับมุมมองไปเป็นของศัตรู** (`subject = team.opponent`)
แล้วให้คะแนนตาม "ตัวนี้ดีต่อศัตรูแค่ไหน" พร้อมถ่วงด้วย `role_fit` ของศัตรู

ตรรกะนั้นสมเหตุสมผลในทางทฤษฎี แต่**ไม่ตรงกับสิ่งที่ทีมอาชีพทำจริง** —
จากข้อมูล ทีมอาชีพแบนตัวที่ presence สูงที่สุดเป็นหลัก โดยยังไม่สนบริบทมากนัก
โดยเฉพาะในเฟสแบนแรกที่ยังไม่มีใครเปิดตัวเลย

ดูจากการแยกตามเฟสจะชัดขึ้น

| เฟส | n | engine | A | C |
|---|---|---|---|---|
| 1·ban | 247 | 0.028 | 0.320 | 0.320 |
| 1·pick | 125 | **0.112** | 0.088 | 0.088 |
| 2·ban | 55 | 0.000 | 0.018 | 0.018 |
| 2·pick | 49 | **0.122** | 0.041 | **0.163** |

เฟสแบนแรก (n=247) คือจุดที่ต่างกันมากที่สุด — A/C ทำได้ 32% เพราะแค่เรียงตาม presence
ส่วน engine ได้ 2.8% เพราะมันพยายามคิดเรื่องตำแหน่งที่ศัตรูยังไม่เปิด
ทั้งที่ตอนนั้น**ยังไม่มีใครเปิดอะไรเลย**

### แต่ชัยชนะบน pick ยังพูดไม่ได้เต็มปาก

| เฉพาะตา pick (n=174) | จุดประมาณ | ช่วง 95% |
|---|---|---|
| engine | 0.115 | [0.076, 0.171] |
| A | 0.075 | [0.044, 0.124] |
| C | 0.109 | [0.071, 0.164] |

```
engine vs A บนตา pick : ยังแยกไม่ออก (ช่วงความเชื่อมั่นทับกัน)
engine vs C บนตา pick : ยังแยกไม่ออก (ช่วงความเชื่อมั่นทับกัน)
```

**engine นำทั้งสองตัว แต่ n=174 ยังเล็กเกินกว่าจะยืนยันได้**
ห้ามอ้างว่า "engine เก่งกว่า baseline ตอน pick" จนกว่าจะขยายตัวอย่าง

## 6. Confidence calibration

วัดโดยดูช่องว่างคะแนนระหว่างอันดับ 1 กับอันดับ 2 ของ engine
เทียบกับความแม่นจริงในตานั้น

| ช่องว่างคะแนน | top-1 แม่น | n |
|---|---|---|
| 0–1 | 0.000 | 26 |
| 1–3 | 0.028 | 247 |
| 3–6 | 0.090 | 111 |
| 6–12 | 0.075 | 40 |
| **12+** | **0.135** | 52 |

**คะแนนของ engine บอกความมั่นใจได้จริง** — ตาที่อันดับ 1 ทิ้งห่าง 12 แต้มขึ้นไป
แม่นกว่าตาที่สูสีถึง 5 เท่า และแนวโน้มเป็นขาขึ้นเกือบตลอด (สะดุดที่ช่วง 6–12 บน n=40)

นี่เป็นผลบวกที่ชัดเจนที่สุดของ engine ในรอบนี้ — **baseline ไม่มีคุณสมบัตินี้เลย
เพราะมันมีแต่ลำดับ ไม่มีคะแนนที่ตีความได้** จึงเทียบกันไม่ได้ในมิตินี้

## 7. ข้อจำกัดของการวัดรอบนี้

1. **`top-1` วัด "ตรงกับทีมอาชีพ" ไม่ใช่ "ถูกต้อง"** ทีมอาชีพเลือกตามผู้เล่นที่ถนัด
   ตามแผนซีรีส์ และตามสิ่งที่ระบบมองไม่เห็นเลย (player pool, การซ้อม, การอ่านคู่แข่ง)
   engine ที่เลียนแบบ 100% จะทำผิดตามเขาทุกครั้งด้วย
2. **ไม่มี metric ที่วัด "คำแนะนำนี้ทำให้ชนะไหม"** ซึ่งเป็นสิ่งที่อยากรู้จริง ๆ
   ต้องใช้ counterfactual ซึ่งข้อมูลที่มีตอบไม่ได้
3. **n=476 โดยรวม แต่บางช่องเหลือ 22** ตัวเลขในกลุ่มเล็กอ่านไม่ได้
   รายงานซ่อนกลุ่มที่ n < 20 อัตโนมัติแล้ว แต่กลุ่มที่เหลือบางกลุ่มก็ยังเล็ก
4. **eval มาจาก 120 วันสุดท้ายเท่านั้น** ถ้าเมตาช่วงนั้นผิดปกติ ผลจะเอนตาม
   ยังไม่ได้ทำ cross-validation หลายช่วงเวลา
5. **199 ตาถูกตัดออก (29.5%)** เพราะตัวที่เลือกจริงมีข้อมูลน้อยกว่า `min_games=5`
   ถ้าลดเกณฑ์ลง ตัวอย่างจะใหญ่ขึ้นแต่ noise ก็มากขึ้น — ยังไม่ได้ทดลอง
6. **calibration วัดบน engine ตัวเดียว** เพราะ baseline ไม่มีคะแนน
   จึงพูดได้แค่ว่า engine calibrate ได้ ไม่ได้พูดว่ามันดีกว่า baseline ในมิตินี้
7. **ลำดับ ban/pick ใน `format.yaml` ยังไม่ยืนยัน** การ replay จึงอาจเรียงตาไม่ตรง
   กับที่แข่งจริง ซึ่งกระทบ "สถานะที่ ranker เห็น ณ ตานั้น" ทุกตัวเท่ากัน
   (ไม่ทำให้การเทียบไม่เป็นธรรม แต่ทำให้ตัวเลขสัมบูรณ์เชื่อได้น้อยลง)

## 8. สิ่งที่ยืนยันว่าไม่มี leakage

`tests/unit/test_benchmark_leakage.py` — 8 เทสต์

| เทสต์ | พิสูจน์อะไร |
|---|---|
| `test_future_hero_has_no_history_in_the_training_pool` | ฮีโร่ที่โผล่เฉพาะใน eval ต้องมีสถิติ = 0 ในชุดที่ใช้ประเมิน |
| `test_pooling_train_and_eval_together_would_have_shown_the_leak` | **ยืนยันว่าเทสต์ข้างบนไม่ใช่ผลบวกลวง** — ถ้ารวมสองชุดจริง ฮีโร่นั้นต้องมีสถิติ |
| `test_compare_rankers_never_sees_eval_statistics` | ตรวจที่ปลายทางจริงด้วย spy ranker ไม่ใช่แค่ที่ `pool()` |
| `test_leakage_guard_rejects_overlapping_sets` | ส่งชุดซ้อนกันต้องโยน `LeakageError` |
| `test_leakage_guard_rejects_train_newer_than_eval` | train ใหม่กว่า eval = เห็นอนาคต แม้ซีรีส์ไม่ซ้ำ |
| `test_every_eval_series_is_newer_than_every_train_series` | คุณสมบัติที่ split ต้องรับประกัน |
| `test_all_rankers_are_scored_on_exactly_the_same_turns` | ตัวหารตรงกันทุก ranker |

**เทสต์คู่ที่สำคัญที่สุดคือสองข้อแรก** — ข้อแรกพิสูจน์ว่าไม่รั่ว
ข้อสองพิสูจน์ว่าข้อแรกจะจับได้จริงถ้ามันรั่ว ถ้าขาดข้อสอง ข้อแรกอาจผ่าน
เพราะเหตุผลอื่นโดยไม่มีใครรู้

| calibration | มีคุณสมบัติ | — | baseline ไม่มีให้เทียบ |

### ข้อเสนอ

**ปัญหาการแบนเป็นเรื่องที่ควรแก้ก่อน M1** — เป็นจุดอ่อนที่ใหญ่ที่สุด วัดได้ชัด
และน่าจะแก้ไม่ยาก (ตาแบนแรกที่ยังไม่มีใครเปิดตัว ควรเอนไปทาง presence มากกว่านี้)

แต่ **การแก้นั้นคือการเปลี่ยนน้ำหนัก/ตรรกะ ซึ่ง PHASE M0.5 ห้ามไว้** จึงบันทึกไว้
เป็นข้อเสนอสำหรับรอบถัดไป ไม่ได้ลงมือในรอบนี้

## 10. ห้ามทำอะไรกับผลชุดนี้

ตาม PHASE M0.5 ข้อ 8

1. **ห้าม fit น้ำหนักจากผลรอบนี้** — ชุด evaluation นี้ถูกดูไปแล้ว
   การปรับน้ำหนักให้คะแนนบนชุดนี้ดีขึ้นคือ overfit ที่มองไม่เห็น
   ถ้าจะ fit ต้องแบ่ง eval ออกเป็นสองส่วนอีกชั้น หรือใช้ช่วงเวลาใหม่ที่ยังไม่เคยดู
2. **ห้ามสรุปว่า engine เก่งกว่า baseline ตอน pick** — ช่วงความเชื่อมั่นทับกัน
3. **ห้ามอ่านตัวเลขในกลุ่มที่ n < 50 เป็นข้อสรุป** — โดยเฉพาะ `B` ในกลุ่มหางแถว
4. **ห้ามเอา `top-1` ไปเป็น KPI** ด้วยเหตุผลใน §7 ข้อ 1
