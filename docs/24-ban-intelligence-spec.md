# 24 — Ban Intelligence Spec

PHASE M0.75 · STEP 2–4 · เขียน **ก่อน** ลงมือและ **ก่อน** ดูผลบน validation

---

## 1. Ban objective

```
Ban ตอบ    "ฮีโร่นี้อันตรายแค่ไหนถ้าปล่อยให้คู่แข่งเลือก"
Pick ตอบ   "ฮีโร่นี้เหมาะกับทีมเราแค่ไหน"
```

สองคำถามนี้ใช้ข้อมูลชุดเดียวกันได้ แต่ **ฟังก์ชันเป้าหมายต่างกัน** —
ห้ามยัดให้สูตรเดียวตอบทั้งคู่เพียงเพื่อ reuse code

### รูปแบบเชิงแนวคิด

```
BanPriority(h) ≈ P(ศัตรูได้ h)  ×  Harm(h ต่อเรา)
```

`P(ศัตรูได้ h)` เป็น**ตัวคูณ** ไม่ใช่ตัวบวก — ฮีโร่ที่แรงมากแต่ไม่มีใครหยิบ
มี BanPriority ต่ำเสมอ ไม่ว่า Harm จะสูงแค่ไหน

นี่คือเหตุผลเชิงโครงสร้างที่ `meta` (ซึ่งประมาณ `P`) ต้องมีน้ำหนักเหนือ `winrate`
(ซึ่งเป็นส่วนหนึ่งของ `Harm`) — **ไม่ใช่ตัวเลขที่จูนมาจาก benchmark**

## 2. BanPriority — feature representation

ตาม STEP 2: เริ่มที่การ**แทนความหมาย** ไม่ใช่การให้น้ำหนัก
ตารางนี้บอกว่าแต่ละ feature มีของอยู่แล้วหรือยัง

| feature | ความหมาย | มีข้อมูลไหม | ใช้อะไรแทน |
|---|---|---|---|
| **Meta Threat** | ทีมอาชีพแย่งตัวนี้แค่ไหน | ✅ | `presence_rate` (component `meta`) |
| **Enemy Access** | ศัตรูหยิบตัวนี้ได้จริงไหม | ✅ | ตัด `locked_by_series(subject)` ออกจาก candidate pool แล้ว |
| **Enemy Likelihood** | เขามีช่องจะใส่ไหม | ✅ (เฟส 2) | `role_fit` บนเลนที่ศัตรูยังว่าง |
| **Our Vulnerability** | ตัวนี้กดทีมเราแค่ไหน | ✅ | `counter` (candidate vs ตัวที่เราเปิด) |
| **Counter Prevention** | ตัวนี้เป็นตัวแก้ของเราไหม | ✅ ทางอ้อม | อยู่ใน `counter` แล้ว |
| **Enabler Prevention** | แบนตัวนี้แล้วเปิดทางให้เราเล่นอะไรได้บ้าง | ❌ **UNKNOWN** | ต้องมี knowledge ว่าอะไรเป็น enabler — ห้ามเดา |
| **Flex Denial** | ตัวนี้เล่นได้หลายเลน ปล่อยไปแล้วเดาไม่ออก | ⚠️ มีข้อมูล ยังไม่มีมิติ | `lane_usage` มีครบ แต่ยังไม่ได้ทำเป็น feature |
| **Draft Phase Context** | เฟสไหน รู้อะไรแล้วบ้าง | ✅ | `turn.phase` + จำนวนตัวที่เปิดแล้ว |

**สามอย่างที่ยังไม่มี** (`Enabler Prevention`, `Flex Denial`, และ `Counter Prevention`
แบบชัดเจน) จะ**ไม่ถูกเพิ่มใน M0.75** เพราะ

- `Enabler Prevention` ต้องใช้ external knowledge ซึ่ง M0.75 ห้ามนำเข้า
- `Flex Denial` เป็น factor ใหม่ ซึ่ง M0.75 ห้ามเปิดน้ำหนัก

บันทึกไว้เป็นงานของ M1 ขึ้นไป

## 3. Phase-aware ban

ตาม STEP 3 — สองเฟสเป็นคนละโจทย์ ห้ามถือว่าเหมือนกัน

| | BAN_PHASE_1 | BAN_PHASE_2 |
|---|---|---|
| รู้ roster ศัตรูแค่ไหน | 0–2 ตัว (ตาแรกคือ 0) | 3 ตัว |
| `counter` / `synergy` | ตายหรือจาง | มีข้อมูลจริง |
| `role_fit` | 1.0 ทุกตัว (เป็นกลาง) | เซ็ตย่อยจริง มีผล |
| สัญญาณที่เหลือ | **meta เกือบล้วน** | meta + counter + synergy + role |

**ข้อสำคัญ: กลไก phase-aware มีอยู่แล้วในโค้ด** — `weights_for(n_enemy, n_ally)`
ไหลตามจำนวนตัวที่เปิดมา ซึ่ง**เป็นการรับรู้เฟสโดยปริยายที่ถูกต้องอยู่แล้ว**

สิ่งที่ขาดคือ *โปรไฟล์* ที่มันไหลเข้าหา ไม่ใช่ *กลไกการไหล*

ดังนั้น M0.75 จะ**ไม่เพิ่ม branch `if phase == 1`** — การแยกเฟสด้วยเงื่อนไข
จะสร้างรอยต่อที่กระโดด และทำให้มี code path เพิ่มโดยไม่จำเป็น

## 4. Minimal fix

ตาม STEP 4 — หาการเปลี่ยนแปลงที่เล็กที่สุดที่แก้ปัญหาได้

### สิ่งที่จะทำ

เพิ่มฟังก์ชันเดียว `ban_weights_for(n_enemy, n_ally)` คู่กับ `weights_for()` ที่มีอยู่
โดยใช้**โครงสร้างเดิมทุกอย่าง** ต่างแค่การแบ่ง `rest` ระหว่าง meta กับ winrate

```python
# pick (เดิม · ไม่แตะ)          ban (ใหม่)
rest * 0.45  -> meta            rest * 0.75  -> meta
rest * 0.55  -> winrate         rest * 0.25  -> winrate
```

การไหลของ `counter` / `synergy` ตามจำนวนตัวที่เปิด **ใช้ของเดิมทั้งหมด**
เพราะเหตุผลของมัน ("ยิ่งเปิดตัวยิ่งมีข้อมูลเฉพาะเกมนี้") ใช้ได้กับทั้งสองโจทย์

### ที่มาของ 0.75 / 0.25 — เป็นการตัดสินใจเชิงโครงสร้าง ไม่ใช่การจูน

1. `BanPriority ≈ P(ศัตรูได้) × Harm` และ `meta` ประมาณ `P` ซึ่งเป็น**ตัวคูณ**
   จึงต้องมีน้ำหนักเหนือ `winrate` อย่างชัดเจน ไม่ใช่แค่เหนือเล็กน้อย
2. `winrate` ไม่ถูกตัดทิ้ง เพราะมันยังเป็นส่วนหนึ่งของ `Harm` จริง —
   ฮีโร่ที่ถูกแย่งพอกันสองตัว ตัวที่ชนะมากกว่าอันตรายกว่า
3. **เลือกค่าเดียว ประกาศก่อนวัด และจะไม่ลองค่าอื่น** ถ้า 0.75/0.25 ไม่ทำให้ดีขึ้น
   จะรายงานว่าไม่ดีขึ้น ไม่ใช่ไล่ลองจนกว่าจะเจอค่าที่สวย
   (STEP 7: ห้ามปรับ weight เพื่อ force benchmark result)

### สิ่งที่จะ **ไม่** ทำ

- ❌ ไม่แตะ `weights_for()` เดิม → pick behavior ไม่เปลี่ยนแม้แต่หลักทศนิยม
- ❌ ไม่แตะ `role_fit` / perspective / candidate pool → audit บอกว่าถูกอยู่แล้ว
- ❌ ไม่เพิ่ม component ใหม่ → M0.75 ห้ามเปิด factor ใหม่
- ❌ ไม่สร้าง Ban Engine แยก → แก้ด้วย architecture เดิมได้

### ผลที่ต้องเป็นจริงโดยอัตโนมัติ

`recommend()` เรียก `ban_weights_for()` เฉพาะเมื่อ `is_ban` เป็นจริง
**ตา pick ทุกตาจึงคำนวณด้วยเส้นทางเดิมทุกบรรทัด** →
`tests/fixtures/recommend_regression.json` ต้องเปลี่ยนเฉพาะตาแบน
และตา pick ต้องเหมือนเดิมเป๊ะ ซึ่งเป็นเทสต์ที่พิสูจน์การแยกสองโจทย์ได้ตรงที่สุด

## 7. การแบ่งข้อมูล (STEP 6)

ห้าม optimize จาก eval เดิมที่ดูไปแล้ว จึงต้องมีสามช่วง **แบ่งตามเวลา ไม่สุ่ม**

```
train (validation setup)   ...          – 2026-02-28
validation                 2026-03-01   – 2026-05-08     ← ยังไม่เคยดู ใช้ตัดสินใจ
─────────────────────────────────────────────────────────
train (holdout setup)      ...          – 2026-05-08
holdout                    2026-05-09   – 2026-09-06     ← รายงานครั้งเดียวตอนจบ
```

**ทำไมต้องมี train สองชุด**

`holdout` คือช่วงเดียวกับที่ [docs/22](22-benchmark-foundation.md) วัดไว้
การใช้ train ชุดเดียวกัน (≤ 2026-05-08) ทำให้ตัวเลขก่อน/หลัง**เทียบกันได้ตรง ๆ**
ถ้าเปลี่ยน train ด้วย จะแยกไม่ออกว่าผลที่ต่างมาจากการแก้โค้ดหรือจากข้อมูลที่น้อยลง

`validation` ใช้ train ที่เล็กกว่าเพื่อให้ไม่คาบเกี่ยวกับช่วง validation เอง

**กติกาที่ผูกมัดตัวเอง**

1. ตัดสินใจทุกอย่างบน `validation` เท่านั้น
2. รัน `holdout` **ครั้งเดียว** หลังตัดสินใจเสร็จ แล้วรายงานตามที่ได้
3. ถ้า holdout ออกมาไม่ดี **ห้ามกลับไปแก้แล้วรันใหม่** — ต้องรายงานว่าไม่ดี
